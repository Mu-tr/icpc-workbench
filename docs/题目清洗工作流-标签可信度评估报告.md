## 一、结论摘要

**总评：工程骨架（版本化、可重建、可人工覆盖、审计留痕）明显优于同类项目，但"最终标签"的可信度目前受制于三类系统性缺陷——口径分裂、信息丢失、版本脱钩。在默认配置下，管线输出的标签"可用但不可全信"，尤其不适合直接当作能力画像的唯一依据。**

| 维度 | 评级 | 一句话依据 |
|---|---|---|
| 架构与可运维性 | **良好** | JSONL 源真相 + 库内索引幂等重建；manual > ai > rule 优先级闭合；差量重跑有版本锚点 |
| 规则层（L1）内部自洽性 | **良好** | 131 条规则，20 条带 `negative` 消歧，加载即校验 code 合法性，单测覆盖关键误配回归 |
| 规则与体系（taxonomy）的一致性 | **一般** | 131 条规则对应 122 个 code；8 个"综合类"code 无课程挂载，成为兜底膨胀源 |
| 标签口径的一致性（跨模块） | **差** | 同一"知识点"存在 **3 套不同实现**（知识点 SQL / 掌握度自建 SQL / 推荐与题单直读 `p.tags`） |
| 信息完整性 | **差** | 管线"红线"主动丢弃题源标签；标注以**替代**而非**补充**方式覆盖口径 |
| 版本与重跑的正确性 | **差** | 标题修复不触发重跑；`rules.json.version` 无任何消费方（死字段） |
| 置信度机制有效性 | **差** | 默认阈值 0.5 vs 规则最低 0.6 / AI 最低 0.5 → **两道闸在默认配置下拦不住任何一条标注** |
| 可观测性 | **一般** | 有 audit.jsonl / coverage / compare / sample；但队列 `attempts`/`last_error`/`failed` 全为死字段 |

**最需要立刻处理的三件事**：① 统一知识点口径（别名归并目标名必须等于 taxonomy `name`）；② 把"标题/难度变更"接入重跑条件；③ 让 `problems.tags` 的写入路径与 `clean-tags` 使用同一套净化规则，否则清洗结果不持久。

### 2.3 数据流转主链路（关键点：三次"身份/语义"变换）

```
平台原始数据
  └─(1) 平台身份归一：problemKey（平台内唯一）· verdict（AC/WA/TLE/RE/MLE/CE）

```

## 三、清洗工作流逐环节拆解

### S0 采集：平台适配器
- **输入**：handle / Cookie / 增量游标（`since`、`knownExternalIds`、`backfillFromPage`）
- **输出**：`NormalizedSubmission[]`（含 `problem{platform,problemKey,title,difficulty,url,tags}`、`verdict`、`submittedAt`、`externalId`）
- **规则**：按新到旧分页、整页已知即早停（增量）、`maxSubmissions` 分批防封号、`truncated/backfill` 续拉
- **已内建的质量补偿**：牛客标题污染清洗（`difficultyBackfill.ts:149-158 cleanNcTitle`）、洛谷 tag id→名称字典（`luogu.ts` / `problemBank.ts:126`）、C3VK 反爬重试
- **风险**：牛客/AtCoder 部分来源无 tags（`problemBank.ts:197/441` 写空数组）；牛客 JSON API 已下线改用 HTML 解析，属结构性脆弱点

### S1 入库规范化
- **难度写策略（**发现矛盾**）**：
  - `bankService.ts:45` → `COALESCE(problems.difficulty, excluded.difficulty)`（**旧值优先**，注释称"用户手动标定的优先"）
  - `importService.ts:30` → `COALESCE(excluded.difficulty, problems.difficulty)`（**新值优先**）
  - 同一字段、两条路径、**相反优先级**：手动标定的难度会被下一次同步覆盖，而题库的新难度永远补不进已有题
- **标签写策略**：`tags = CASE WHEN excluded.tags != '[]' THEN excluded.tags ELSE problems.tags END`（两处一致）
  - 后果：**非空即覆盖**。`POST /api/problems/clean-tags` 物理清洗后的规范化标签，会被下一次 CF/洛谷同步的原始英文标签整批覆盖 → **清洗不持久**
- **L1 钩子**：事务提交后调用，失败仅 `console.error`（标注失败不影响入库，设计合理）

### S2 难度标尺归一
| 平台 | 映射 | 位置 |
|---|---|---|
| 洛谷 | 分级 0–8 → {1:1000,2:1300,3:1500,4:1700,5:2000,6:2300,7:2600,8:3000}，`d<=0` → null | `luogu.ts:47` |
| LeetCode | easy/medium/hard → 1200/1600/2100 | `leetcode.ts:54` |
| AtCoder | 预估难度四舍五入，`<800` 钳到 800 | `problemBank.ts:430-433` |
| 计蒜客 | level1–8 → 800/1000/1300/1600/1900/2200/2500/2800 | `jisuanke.ts:117` |
| 牛客 | 需 `^\\d+$ && ≥100` 才认（滤演示脏数据） | `problemBank.ts:222` |

问题：**四种标尺压缩到同一条 rating 轴，但语义不等价**（力扣 medium=1600 与洛谷提高=1700 的"能力含义"差异很大）；且分桶边界（`stats.ts:11-16`：1200/1400/1600/1900/2200）与各平台原始分级粒度不匹配 → 难度画像的跨平台可比性弱于标称。

### S3 题源标签落库
- **规则**：原样 JSON 数组存入 `problems.tags`，**写入路径不做任何净化**（全仓 `filterNoiseTags` 只出现在 analysis/plans/routes，不在 adapters/import）
- **定位**（`schema.sql:68`）："平台原始 tags 仅作审计数据"

### S4 L1 规则标注（确定性）
- **输入**：**仅** `platform / problemKey / title`（`pipeline.ts:47-51`，明确不含题源 tags、不含难度）
- **规则**：`rules.json` 131 条，`pattern`/`negative` 为正则源码，统一 `i` 旗标；同 code 多命中取最高置信度；`method = rule#rNNN`
- **输出**：命中 → `problem_keypoints(source='rule')`；未命中 → `knowledge_queue(status='pending')`
- **版本**：`PIPELINE_VERSION=3`、`taxonomy.version=2`；`rerun` 只选 `source='rule' AND (pipeline_version < 3 OR taxonomy_version < 2)`

### S5 L2 AI 标注 / 无 Key 导出通道
- **输入**（红线）：批内 `problemKey + title + difficulty` + taxonomy 候选清单（**不给题源 tags**，`aiClassify.ts:55-74`）
- **四道闸**：围栏清洗（`cleanJsonText` 字符串感知括号配对）→ schema 校验 → taxonomy 白名单（幻觉 code 丢弃并写 audit）→ 置信度阈值
- **置信度规则**：AI 单值 − 序号×0.05，**下限 0.5**（`aiClassify.ts:157`）；缺失字段默认 0.6
- **队列语义**：批次失败**整批保持 pending 且立即返回**（不标 failed，避免网络抖动打死题）；`uncertain` 表示 AI 也判不出
- **导出通道**：默认 50 题/包（`EXPORT_BATCH_SIZE`），`/export-queue` 上限 1000；回填走同一套校验，`method='ai:manual-import'`

### S6 L3 人工校正
- `PUT /api/knowledge/:platform/:key` → `setManualKeypoints`：**清除该题全部来源标注**后写 `source='manual'`（confidence=1），并为 rule/ai 各补一条 **tombstone** 空快照防 JSONL 重放复活
- 空数组 = 人工确认"无知识点"（语义完整，是个好设计）

### S7 存储与重建
- **源真相**：`data/knowledge/annotations.jsonl`，每行 = 某题某来源的**完整快照**；DB 写入与 JSONL 追加在同一事务窗口（先 append 后 COMMIT）
- **重建**：启动时 `loadAnnotationsIntoDb` 幂等重放，按（题 × 来源）取最后一行，各来源并集，同 code `manual > ai > rule`；taxonomy 中不存在的 code 丢弃并计数
- **读取**：`knowledgeTagsSql`（`store.ts:302-311`）三级回退，`confidence >= 阈值`（默认 0.5）

### S8 消费口径（分裂点）
| 消费方 | 读什么 | 位置 |
|---|---|---|
| stats / weakness / summary / problems / today / reviews | `knowledgeTagsSql`（三级回退） | `stats.ts:72`、`problems.ts:40` 等 |
| mastery 掌握度 | **自建 SQL**：keypoints 聚合 by code + 未覆盖回退 `p.tags`（`CASE WHEN EXISTS … THEN '[]' ELSE p.tags`） | `mastery.ts:142-156` |
| **planService 推荐选题** | **直读 `p.tags`** | `planService.ts:363/436/975` |
| **lists 题单分类** | keypoints → 即时 L1 → `classifyByTags(p.tags)` 三级混合 | `lists.ts:78-92` |

## 四、标签可信度评估（逐项结论 + 依据）

### 结论 1｜口径分裂：同一"知识点"有 3 套互不等价的实现 —— 严重

**依据**
1. `plans/planService.ts:378-407`（以及 `:970-1010`）取弱项标签集合来自 `computeWeakness`（**知识点口径**，产出如「二分查找」「线段树」），而候选题标签取自**原始 `p.tags`** 再 `canonicalTag` 归并（产出如「二分」「数据结构」）。打分语句 `tags.filter(t => weakTags.has(canonicalTag(t)))` 因此在失配集合上恒为 0 → **弱项定向命中静默失效**。
2. 失配并非个例：核验脚本显示 18 条别名映射中 **9 条的目标名在 taxonomy 中不存在**（详见结论 3）。
3. `lists.ts:24-34` 的分类体系直接由别名映射的**值**构成（`Object.values(TAG_ALIAS_TO_CANONICAL)`），与 taxonomy 的 122 个 `code/name` 是两套名词系统。
4. 中间层 `problem_topics` 属遗留：`TOPIC_TAGS_SQL`（`topics/pipeline.ts:26`）**无任何引用方**，该表只在用户手动点 `POST /api/problems/topics/rebuild` 时才有数据 —— 但它仍被 `knowledgeTagsSql` 当作第 2 优先级回退，构成"幽灵数据源"。

**可信度影响**：弱项画像、掌握度地图、推荐选题、题单分类给出的"同一知识点"结论互不可复现；用户看到的是"系统里有两套标签"。

---

### 结论 2｜信息丢失：管线主动丢弃质量最高的信号 —— 严重

**依据**
1. **红线设计**：`pipeline.ts:3` 明确"入管线即丢弃题源 tags，特征只有 platform/problemKey/title/difficulty"。而 Codeforces 官方 tags（`codeforces.ts:19,140`）与洛谷 tags（`luogu.ts:225`）恰恰是**平台侧已标注的人工/官方结果**，质量显著高于"仅凭标题推断"。
2. **替代而非补充**：读取 SQL 是 `CASE WHEN EXISTS(keypoints≥阈值) THEN 只返回 keypoints`（`store.ts:305-309`）。因此一道 CF 题一旦被 L2 判出 1 个 code，其原有的 3–5 个平台标签**全部退出统计口径**。以"贪心"单标签覆盖掉 `dp, greedy, math` → 弱项画像少计 DP。
3. **审计链断裂**：`classifyTitle` 返回的 `ruleIds`（"命中了哪几条规则"，注释称为审计用）在落库时被丢弃 —— `writeAnnotationsToDb`（`store.ts:237-242`）只写 `code/confidence/method`，`schema.sql` 也无对应列。冲突合并后 `method` 只保留最高置信的那一条 → **"可解释、可审计"只到单条规则粒度**。
4. **人工校正的副作用**：`setManualKeypoints` 清除全部来源标注。若人工只补一个 code，原先 rule/ai 的其它 code 一并消失（设计上"校正即定论"，但对多知识点题目是信息净损失）。
5. **JSONL 单点**：启动重建先 `DELETE FROM problem_keypoints`（`store.ts:153`）再重放。若 `annotations.jsonl` 丢失/未初始化而 DB 有数据 → **标注全量清空**，无二次备份。

### 结论 3｜误判与错误归并：具体可举证的案例 —— 严重

**依据**

**(a) 别名归并目标名不存在（9/18）** —— 核验脚本实测：

| 平台标签 | 归并目标 | taxonomy 中同名 code |
|---|---|---|
| `binary search` | 二分 | ✗（实际为「二分查找」） |
| `data structures` | 数据结构 | ✗（仅大类名） |
| `dfs and similar` / `depth-first search` | DFS | ✗（实际为「DFS 与回溯」） |
| `graph matchings` | 二分图 | ✗（实际为「匈牙利算法」） |
| `hash table` / `hashing` | 哈希 | ✗（实际为「字符串哈希」） |
| `bit manipulation` | 位运算 | ✗（实际为「位运算技巧」） |
| `probability and statistics` | 概率期望 | ✗（实际为「期望 DP」） |
| `game theory` | 博弈论 | ✗（实际为「博弈论基础」） |

`mastery.ts:142` 用 `nameToCode = new Map(allPoints().map(p => [p.name, p.code]))` **精确匹配**，所以这些目标名归并不进去 → **同一知识点裂成两个点**：「二分查找」（有 taxonomy code，可能停在"未开始"）+「二分」（幽灵点，累积真实通过数）。README 第 16 条宣称的"binary search ↔ 二分 自动归并、同一知识点不分裂"**在该映射上不成立**。

**(b) 规则误配**（`rules.json`）：
- `r142`：`莫比乌斯|莫反|mobius|数论分块` → `math.mobius`（0.9）。标题「数论分块」被定为**莫比乌斯反演** —— 数论分块是可独立存在的技巧，此处是概念混淆。
- `r141`：`FFT|NTT|快速傅里叶|多项式` → `math.fft`（0.85）。任何含「多项式」的题（多项式哈希、多项式求逆）都会挂 FFT。
- `r086`：`期望|概率|probabilit|expect` → `dp.probability`（0.7）。`expect` 无词边界，是子串匹配。
- `r171`：`哈希|hash` → `string.hash`（0.6）。泛词，且与 `r170`（字符串哈希 0.9）同 code，实际把大量"哈希表/哈希集合"题归入**字符串哈希**。
- `r050`：`堆` → `ds.heap`（0.6）；`r197`：`排序` → `misc.sorting`（0.7）；`r030`：`搜索` → `search.general`（0.6）。这些**兜底泛词**会把「拓扑排序」「后缀排序」等同时计入泛类桶。

**(c) 兜底泛类膨胀**：`r091 动态规划 / r105 最短路 / r149 数论 / r171 哈希 / r187 几何 / r197 排序 / r030 搜索 / r172 字符串` 等"综合类"code 大量命中，而它们恰好是**没有挂课程模板的 8 个 code**（`search.general, dp.general, graph.shortest-path, math.number-theory, math.combinatorics, string.general, geo.general, misc.sorting`）。结果：掌握度地图上出现一批**无"看课"入口、纯由兜底规则堆积**的知识点，其 `solved/acRate` 是多个真实知识点的混合平均，**没有诊断意义**，却会挤占统计列表。

**(d) 标题被修复但标注不刷新** —— 最隐蔽的一类误判：
- 牛客标题污染是**已确认的历史问题**（`difficultyBackfill.ts:149-158`），且修复路径会改写 `problems.title`。
- 但重跑条件只有 `pipeline_version / taxonomy_version`（`pipeline.ts:129-134`），**与 title 变更完全脱钩**；`annotateProblemsL1` 又对"已有任意标注"的题直接 `continue`（`pipeline.ts:76`）。
- 结论：**基于污染标题（含换行+标签串的脏 title）产生的标注会永久驻留**，且用户点"重建/重跑"也不会被选中修复。

---

### 结论 4｜规则不一致（同一语义在不同环节有不同规则）—— 中等偏严重

| # | 不一致点 | 位置 | 后果 |
|---|---|---|---|
| 1 | 难度优先级相反 | `bankService.ts:45` vs `importService.ts:30` | 手动/回填难度被同步覆盖；题库新难度永不更新 |
| 2 | 清洗只在读时+一次性写时，写路径不净化 | `problems.ts:142-164` vs adapters | `clean-tags` 结果被下次同步覆盖 → 清洗不持久 |
| 3 | `rules.json.version` 无消费方（`rulesVersion()` 零引用） | `ruleEngine.ts:70` | 改规则忘 bump `PIPELINE_VERSION` → **静默陈旧**，差量重跑不触发 |
| 4 | 默认阈值 0.5 = AI 置信下限 0.5、规则最低 0.6 | `store.ts:18`、`aiClassify.ts:157`、`rules.json` | 「置信度闸门」在默认配置下**拦不住任何一条**，`getCoverage.annotated ≡ withAny` |
| 5 | 题单分类三级混合（keypoints → 即时 L1 → tags 归并） | `lists.ts:78-92` | 同一题在"题目管理"与"题单整理"显示不同分类 |
| 6 | 队列状态机未闭环：`markQueueStatus` 零调用 | `pipeline.ts:175`、`aiClassify.ts:17` | `attempts/last_error/failed` 全为死字段；批次失败后**每轮从头重试同一批 25 题**，无退避、无上限 |

### 结论 5｜引入偏差（系统性、可量化）—— 中等

1. **语种偏差 → 平台偏差（已有实测数据）**：131 条规则里 91 条含拉丁词，但"高置信规则（0.9）"绝大多数以中文关键词为主（如 `【模板】线段树`）。CF/AtCoder 题面为英文且标题高度抽象（如 `Xor Sequences`），**L1 命中率天然低于洛谷**（洛谷题名有「【模板】×××」「××× 板子」等强信号）。
   - **项目日志实测：真实库 19143 题跑 L1，仅 1241 题命中，覆盖率 6.5%**（余下 93.5% 全部落入 L2 队列）。这意味着**当前标签的主体来自 L2 的"标题 + 难度"推断**，而不是确定性规则。叠加"红线丢弃题源标签"后，CF 的知识点几乎完全由 L2 产生 —— 这是同一套体系里最大的偏差来源，也意味着**标签可信度的上限由 AI 标题猜测的准确率决定**。
   - 该覆盖率同时说明：`uncertain`（AI 也判不出）与 `pending` 的规模会远大于已标注量，用户"清空队列"的动机很强，进一步放大结论 5.3 的凑数风险。
2. **多标签衰减是人为的**：`confidence − i×0.05` 只依赖 AI 输出顺序，不反映真实把握；且下限 0.5 使"排序衰减"在阈值过滤上**完全无效**（连第 10 个 code 也 ≥0.5 通过）。
3. **`uncertain` 长期滞留**：AI 判不出的题保持 `pending/uncertain`，无权重、无优先级、无失败上限 → 队列尾部永远是"标题信息量最低的题"，即**最难标注、也最容易被凑数标注**的一批；一旦用户为了清空队列反复重跑，AI 在"必须给出答案"的语用压力下倾向于输出低质量 code（当前提示词虽有"拿不准返回空 codes"，但无置信度校准约束）。
4. **难度桶跨平台不可比**（见 S2）：`1200-1399` 桶内可能同时是"洛谷普及-"与"力扣 medium"级别的题，难度弱项结论的可解释性被稀释。
5. **样本权重偏差**：`weakness` 按**提交次数**计数（`weakness.ts:46-56` 逐 submission bump），一道反复 WA 的题会把该知识点 AC 率显著拉低；没有按题目去重的口径与之对照（`solved` 仅作展示）→ 容易把"刷错题"误读成"知识点弱"。

## 五、影响标签可信度的关键风险点（按优先级）

### P0（直接污染结论，建议优先修）
1. **别名归并目标名与 taxonomy `name` 不一致（9/18 失配）** → 知识点分裂 + 推荐/弱项命中失效。**影响面**：弱项画像、掌握度地图、推荐选题、题单分类。
2. **标注"替代"题源标签 + 红线丢弃平台高质标签** → 信息净损失，CF/AtCoder 尤甚。
3. **标题变更不触发重跑** → 基于脏标题的误判永久驻留（牛客标题污染已有实证）。
4. **`rules.json.version` 无消费方** → 规则迭代静默失效。

### P1
5. 难度字段两条路径相反优先级（数据被覆盖/永不更新）。
6. `clean-tags` 结果不持久（写路径不净化）。
7. AI 批内 `problemKey` 跨平台重名 → 只落一条、另一条滞留；**手工导入通道更严重**：`importAiResults` 以 `problem_key` 单键回查队列（`aiClassify.ts:275-290`），跨平台同名行会被 `Map` 去重，未写入的那条**永久停在 pending**。
8. 队列状态机死字段 + 无退避重试策略（成本与进度风险）。

### P2
9. 默认阈值使置信度闸门失效；`getCoverage` 因此高估"有效覆盖率"。
10. `ruleIds` 未落库 → 审计粒度不足（对外宣称"可审计"存在落差）。
11. `problem_topics` 幽灵回退层（`TOPIC_TAGS_SQL` 零引用但被 SQL 引用）。
12. JSONL 单点：文件丢失 = 标注全丢，无二次备份（与项目已有的"恢复点"体系未打通）。
13. 多注释义衰减无效（`−0.05×i` 且下限 0.5）。
14. 弱项按提交次数计权，缺少按题去重的对照口径。

## 六、可改进之处（可落地建议）

### 立刻可做（低风险、高收益）
1. **统一名词系统**：把 `TAG_ALIAS_TO_CANONICAL` 的**值**改为 taxonomy 的 `code`（而非中文名），`canonicalTag` 返回 code；或在 `mastery.ts` 用"别名目标 → 最近 taxonomy name"的显式映射表补齐那 9 条。并在 `knowledge-rules.test.ts` 增加断言：**每条别名映射目标必须能解析到 taxonomy 的某个 `code`**（把这条不一致变成编译期/测试期错误）。
2. **标题/难度变更接入重跑**：给 `problems` 增加 `title_hash`（或 `annotated_title`），`runRulePass({rerun})` 的 WHERE 增加 `OR k.source='rule' AND p.title_hash != k.title_hash_at`；`difficultyBackfill` / `cleanNcTitle` 改写标题后同步失效标注。
3. **规则版本接入差量重跑**：在 `problem_keypoints` 增加 `rules_version` 列（或用 `pipeline_version = PIPELINE_VERSION` 与 `rulesVersion()` 组合成复合版本号），消灭"忘 bump"的静默失败；同时删除或真正使用 `rulesVersion()`。
4. **难度写策略二选一并写死**：建议统一为"**显式优先级**：manual > backfill > sync > bank"，并在 `upsertBankProblems` / `insertNormalized` 使用同一段 SQL（可抽 `problemWritePolicy.ts`）。
5. **标签写入净化 + 幂等**：在 adapters/import 落库前调用 `filterNoiseTags(...).map(canonicalTag)`，让 `clean-tags` 从"一次性维护操作"升级为"写入即满足的不变量"，消除"被下次同步覆盖"的问题。

### 结构改进（中等成本）
6. **把"标注替代"改为"标注叠加"**：`knowledgeTagsSql` 建议改为 `keypoints(≥阈值) ∪ (题源 tags 中未被任何 keypoints 覆盖的概念)`，或在 `problem_keypoints` 引入 `relation='primary|secondary'` 与 `source_tags_snapshot`，避免单标签覆盖整题口径。若担心噪声，可对题源标签给一个固定的"先验置信度"（如与 keypoints 同权重的 0.7），纳入统一加权而非二选一。
7. **AI 输入补齐上下文**：在红线允许范围内加入 `platform` + 题源标签的**受控使用**（例如仅作提示词中的"参考，不得直接采信"），并对 `problemKey` 加平台前缀（`<platform>|<key>`）作为批内唯一键，修掉跨平台重名。
8. **队列状态机落地**：`runAiPass` 调用 `markQueueStatus`，失败批次写 `attempts+1`、`last_error`，`attempts >= N` 转 `failed` 并出队（另存待复核清单）；批次失败的 `pending` 改为**移到队尾**（`enqueued_at` 更新）避免队首阻塞；给 `runAiPass` 加默认 `maxBatches` 上限与明确的"未完成"返回语义。
9. **置信度机制生效**：默认阈值建议提到 0.6–0.7（与规则最低置信度对齐），让 AI 的 `Math.max(0.5, …)` 下限改为可配（如 0.3），并把 `getCoverage` 拆成"≥阈值 / <阈值 / 未覆盖"三栏，让覆盖率指标真实反映低置信占比。
10. **兜底泛类隔离**：`*.general` / `最短路` / `数论` 等 8 个无课程 code 建议在统计与地图中**单独分区展示**（或只用于筛选、不参与弱项 gap 排名），避免混合平均误导。
11. **审计粒度补齐**：在 `problem_keypoints` 增加 `rule_ids TEXT`（JSON 数组）与 `evidence TEXT`，把 `RuleMatch.ruleIds` 落库；`audit.jsonl` 增加"重跑差异"记录（旧 code 集 → 新 code 集）。
12. **JSONL 保护**：启动重建前对 `annotations.jsonl` 做一次 `VACUUM INTO` 式快照并纳入现有"恢复点"体系；重放前校验行数单调性，异常时拒绝 `DELETE`。

### 验证手段（已有设施，建议常态化）
13. 项目已具备极好的自检设施：`GET /api/knowledge/compare`（双口径 top 对比 + uncovered 桶）、`/sample`（随机抽检）、`audit.jsonl`、`coverage`。建议把 compare 的 `uncovered` 占比与"别名失配导致的漏配率"做成**回归基线**，纳入 `npm test`（当前 `knowledge-rules.test.ts` 已测规则/负例，但**未测别名映射与 taxonomy 的对齐**、也**未测 planService 的弱项命中率**）——这两条正是本次发现的最大盲区。
