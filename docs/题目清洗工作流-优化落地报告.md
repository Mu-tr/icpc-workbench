## 三、逐项说明

### 1. 标签同义词体系：从「按名映射」改为「按 code 锚定」

**问题**：旧实现是一张 41 条的 `别名 → 中文名` 平表。它的目标词是**课程词表**（「二分」「DFS」「哈希」），而 taxonomy 用的是另一套名字（「二分查找」「DFS 与回溯」「字符串哈希」）。后果是 `computeMastery` 的 `nameToCode.get(tag)` 拿不到 code，于是同一知识点在掌握度地图里裂成两个点：CF 题标 'binary search' 出一个「二分」，而管线标注的题出「二分查找」。

**改动**：
- 新建 `shared/src/tags.ts`，把映射改为 **129 个「组」结构**：`{ name, code?, tags[] }`，其中 `name` 必须等于该 `code` 在 `taxonomy.json` 里的 `name`。
- `expandTag()` 从「自身 + 英文名 + 反查别名」改为**返回整组同义词**——这是课程联动的关键：规范名是「二分查找」，而课程模板的 tag 是「二分」，靠整组展开才连得上。
- 文件头写明 5 条设计不变量，并在 `knowledge-rules.test.ts` 里逐条断言。

**迁移安全性**：写脚本逐条核对旧表 41 个键 → 新规范名，要求每个新规范名都落在「taxonomy 名 ∪ 课程 tag」内，且旧目标仍在同义组内。脚本抓出我自己的 3 个错误：

| 自查发现的缺陷 | 后果 | 修法 |
|---|---|---|
| `flows` / `matrix` 未归并（旧表有，新表漏） | 归并目标变回裸英文 → 新死点，课程也挂不上 | 'flows' 并入「Dinic 最大流」组，'matrix' 并入「矩阵快速幂」组 |
| 「暴力 / 暴力枚举 / brute force」被并入 `search.general` | 通用兜底桶被撑大，掩盖真实弱项 | 从该组移除，保持与迁移前一致的「未覆盖桶」行为 |

**验证**：`computeMastery` 测试改为断言规范名 + `code === 'basic.binary-search'` + 课程联动 `templates.length > 0`。

### 2. 规则版本真正接入差量重跑

**问题**：`rulesVersion()` 零引用。改了 `rules.json` 却忘了改 `PIPELINE_VERSION`，差量重跑就不会选中任何题——"静默失效"。

**改动**：
```ts
export const PIPELINE_CODE_VERSION = 4;
// 管线版本 = 代码版本 × 1000 + rules.json 版本 → 4 * 1000 + 1 = 4001
export const PIPELINE_VERSION = PIPELINE_CODE_VERSION * 1000 + rulesVersion();
```
`rulesVersion()` 加进程内缓存（此前每次调用都读盘）。`GET /api/knowledge/meta` 现在分别输出 `pipelineCodeVersion` / `rulesVersion` / `rules` 条数，排查时能直接定位是哪一段变了。

**代价**：版本号从 3 跳到 4001，所以首次 `rerun` 会把全部 rule 标注重跑一遍（实测库约 1200 条，秒级）。这正是一次性、必要的失效重建。

### 3. 标题指纹：标题被修复后标注自动失效

**问题**：`cleanNcTitle`（牛客标题污染修复）与题库回填会改写 `problems.title`，而重跑条件里没有标题变更这一项——基于旧标题的误判标注会**永久驻留**。

**改动**：
- `problem_keypoints` 增 `annotated_title` 列，记录**标注当时的标题**（rule 与 AI 两侧都写）。
- 重跑条件增加 `OR k.annotated_title IS NOT p.title`（`IS NOT` 同时覆盖 NULL）。
- 新增 `requeueStaleAiByTitle()`：标题变了之后 AI 标注同样陈旧，把它重新放回 L2 队列。
  **这里刻意采用保守口径**——只处理"有指纹且不符"的行；升级前遗留的 `annotated_title IS NULL` 的旧 AI 标注**不**被翻出来，避免升级后一次性重跑全量 AI（那是真金白银）。

**验证**：两条新测试——rule 侧（改标题 → `scanned=1` → 过期 rule 标注清除 → 重新入队）；AI 侧（改标题 → 回队；抹掉指纹 → 不再回队）。

---

### 4. 跨平台同题号不再串题

**问题**：`problemKey` 只在平台内唯一（洛谷 P1001 与某 CF 1001 是两道题），但 AI 批分类的输入输出都只有裸题号。批内一旦重名，`new Map(batch.map(b => [b.problemKey, b]))` 会静默丢掉一道，AI 也可能把知识点贴到另一平台的题上。

**改动**：
- 新增 `problemIdentity(platform, key)` → `luogu|P1001`；提示词改为回抄 `id`，并明确告知"只回题号会导致贴错题"。
- `parseClassifyResponse` 同时接受 `id`（新）与 `problemKey`（旧的导出包/手搓 JSON）。
- `validateItems` 裸题号在批内有多义时 → 记 `ambiguous` 审计、**不猜平台**，且不让这些题落入 `uncertain` 出队（否则永远无法被修正）。
- `importAiResults` 支持复合身份直查 `problems`。
- 新增**无进展守卫**：整批只产出 `ambiguous` 时既不写库也不出队，会取到同一批空转 → 立即返回 `stalled`。

**验证**：三层——`validateItems` 单元（复合身份精确落题 / 裸题号歧义不猜）、端到端（`importAiResults` 后另一平台的题 `keypoints` 为 0）、契约（`ref` 字段与新旧两种 JSON）。

### 5. 队列状态机闭环

**问题**：`markQueueStatus` 零调用，`attempts` / `last_error` / `failed` 全是死字段；批次失败后每轮从队首重取同一批 25 题，毒批永久阻塞队首。

**改动**：
| 机制 | 行为 |
|---|---|
| `markBatchRetry` | 整批失败：`attempts + 1`、写 `last_error`、**把 `enqueued_at` 推到队尾**（关键：下一轮从别的批开始） |
| `MAX_ATTEMPTS = 3` | 达到上限的题转 `failed` 出队，不再反复重试 |
| `retryFailedQueue` | `POST /api/knowledge/retry-failed`，把 `failed` 捞回 `pending` 且 `attempts` 清零 |
| `getCoverage` | 新增 `retrying`（pending 且 attempts>0）与 `failed`，前端在「知识点管线」面板展示并可一键捞回 |

**验证**：一条测试连跑 3 轮失败，逐轮断言 `attempts`、`status`、`retried`/`gaveUp` 与 `coverage.failed`，最后断言捞回后 `attempts=0`。

---

### 6. 难度来源优先级统一

**问题**：`importService` 用 `COALESCE(excluded, existing)`（新值优先），`bankService` 用 `COALESCE(existing, excluded)`（旧值优先）——同一字段两条路径**优先级相反**，导致「手动标定的难度被同步覆盖」与「题库补的新难度进不了已有题」同时存在。

**改动**：新建 `problemWritePolicy.ts` 作为 `problems` 表 upsert 的**唯一实现**：
```
manual(4) > backfill(3) > sync(2) > bank(1)
```
新值非空且来源优先级 ≥ 已有优先级才覆盖。历史 NULL 视为 `'sync'`（与迁移前行为等价）。`difficultyBackfill` 的两条 UPDATE 显式标 `'backfill'`。

> **运维须知**：`difficulty` 与 `difficulty_source` 必须同写。用裸 SQL 改难度而不动来源，等于把该题的难度降回 `'sync'` 优先级，之后会被题库刷新覆盖。

---

### 7. 标签净化下沉到写入路径

**问题**：清洗（噪声过滤 + 同义词归并）只在 **读取** 时做、外加一个手动按钮 `POST /api/problems/clean-tags`。所以"清洗过的结果"会被下一次同步原样覆盖回脏标签。

**改动**：`purifyTags()` = `filterNoiseTags` → `canonicalTag` → 去重，接入 `importService` / `bankService` / `difficultyBackfill` 三处写库点。`clean-tags` 保留，但语义明确为「修复引入净化前遗留的历史数据」，新数据上它是幂等的。

**为什么安全**：`weakness.ts` / `mastery.ts` / `problems.ts` 的读取路径**本来就在做** `canonicalTag`，所以写入时先归并**不改变任何统计结果**，只是让库内数据与分析视图一致。

---

### 8. 置信度机制修正

**问题**：规则表最低置信度是 `0.6`，而统计端默认阈值是 `0.5`，AI 多 code 降权下限也是 `0.5`——**默认配置下阈值闸门拦不住任何一条标注**，形同虚设。

**改动**：默认阈值 `0.5 → 0.6`；AI 降权下限 `0.5 → 0.35`（让多知识点题的第 2、3 个点能落到阈值之下，闸门才有过滤能力）。设置页初值同步。

---

### 9. 知识点源真相纳入恢复点

**问题**：备份是纯 `.db`（`VACUUM INTO`）。而知识点标注的**源真相是 `data/knowledge/annotations.jsonl`**，启动时 `loadAnnotationsIntoDb` 会用它重建 `problem_keypoints`。只回滚数据库不回滚 JSONL = 恢复点在知识点上**完全无效**（更晚的 JSONL 立刻覆盖回来）。

**改动**：
- `createBackup` 同时把 `annotations.jsonl` 逐字节快照为同名的 `xxx.knowledge.json`。
- `applyPendingRestore` 恢复数据库后同步回滚该文件；旧备份（无快照）走兼容分支，只回滚数据库并明确告警。
- `pruneBackups` 成对删除；`listBackups` 暴露 `knowledge: boolean`，前端在列表与恢复确认框里提示。
- `audit.jsonl` **有意不纳入**：它是追加型审计日志而非状态，回滚它只会白丢排查线索。

**顺带修掉一个真实缺陷**：同一秒内连续备份会生成带毫秒后缀的退避文件名（`icpc-...-manual-123.db`），而文件名正则的 reason 段是 `[a-z-]+`（不含数字），**匹配失败** → 这些文件对 `listBackupFiles` 不可见 → **永远进不了保留策略的清理集合**。用户连点几下「立即备份」就会留下永不回收的文件。已把可选毫秒后缀纳入正则（由「快照数 = .db 数」的配对断言暴露）。

---

### 10. 删除幽灵回退层副本

`topics/pipeline.ts` 的 `TOPIC_TAGS_SQL` 是零引用常量，内容与 `knowledge/store.ts` 的 `knowledgeTagsSql()` 中的 `problem_topics` 回退分支**逐字重复**——两份拷贝各改各的正是口径漂移的来源。已删除，并在两侧注明这是该三级回退链的唯一实现。

## 四、行为变更与升级须知

### 4.1 库内 `problems.tags` 内容会变（一次性）
写入即净化后，库内标签变成规范名（`dp` → `动态规划`、`binary search` → `二分查找`）。**统计结果不变**（读取路径本就归并），但：
- 题目列表、题单分类里显示的标签名会变（题单分类目录现在直接取 taxonomy 规范名）。
- 原始题源标签**不再保留**在 `problems.tags` 里（此前点一次 `clean-tags` 也会同样销毁，只是现在提前到写入时）。原始标签仍可从平台侧重新拉取。

### 4.2 `clean-tags` 不再是"维护步骤"
新数据上它是空操作。老库升级后**建议手动点一次**，把净化前写入的历史脏标签一次性归并。

### 4.3 首次升级会触发一次全量 rule 重跑
`PIPELINE_VERSION` 3 → 4001，首次 `版本差量重跑` 会把全部 rule 标注重算一遍。这是预期的一次性失效重建，耗时秒级。

### 4.4 数据库自动迁移
`migrate()` 新增两段（幂等，仅在列缺失时执行）：`problem_keypoints.annotated_title`、`problems.difficulty_source`（并对已有非空难度回填 `'sync'`）。

## 五、尚未落地（按价值排序）
